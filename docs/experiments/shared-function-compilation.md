## Shared boundary

B extracts established integer binary arithmetic/comparison folding and deterministic register-copy scheduling. Unary conversion handling, target moves/swaps, machine windows and instruction selection remain target code. All 14 fixed modules have identical A/B native-code SHA256 hashes on **both AMD64 and ARM64**. ARM64 code was generated by an ARM64 compiler binary under QEMU; this is code-generation evidence, not native ARM64 execution or timing. Production helper code decreases by 114 lines; the parity tests add 232 lines. Source-line reduction is a maintenance result.

C introduces `shared.ScalarState.CompileScalar`, which consumes validated encoded bytecode directly and emits through `ScalarTarget`. It is one actual shared driver, not wrappers around the old body drivers. Both target `runBody` methods select it after admission. The old logical stack, target local tracker and target control driver are unused for the admitted body. Existing scratch backing can remain allocated for fallback, but does not supply a second authoritative semantic state.

The common layer owns the operand stack, stable arena identities, reference-counted local versions and deferred parent edges; locations, register ownership and borrowing; spill-slot reuse, canonical joins and return preparation. A local's current identity/location conservatively determines whether its home is valid: a borrowed home is clean, a changed/materialized register binding requires reconciliation. The pilot does not preserve every clean-home optimization. Shared value IDs remain stable when spills move values. Deferred expression depth is capped at six. Memory/immediate operands and direct deferred comparison-to-branch lowering are retained; scaled add retains target LEA/add-shifted selection.

The target supplies physical register order/reservations, fixed-register clobbers, operand legality, offsets, encodings, moves/loads/stores, branches/patches and ABI return details. Nested fixed-register lowering reconsults stable value IDs after descendants may spill operands. Only the GP bank is admitted. FP/vector signatures and values use fallback.

Joins use canonical local homes and reserved operand slots. Borrowed/deferred values are captured before any home is overwritten, then both edges agree on locations. Temporary spill slots start after the canonical operand range. This is correct but deliberately conservative. AMD64's linked-node stack and ARM64's slice stack remain unchanged for fallback. The common driver uses its own representation, without a target representation-conversion commit. ARM64 `lsReg` is numerically zero, but the current recorded packed-merge invariant requires a nonzero memory/clean entry, allowing the legacy all-zero absent sentinel. Shared controls use explicit frame presence and `-1` branch-site sentinels; they do not reuse that packed representation.

There is no instruction object array, mandatory SSA pass or full-function IR. Admission stores bounded summaries; emission streams a second read of the immutable body. Its arena retains value records within a function, including dead records, and is reused across functions of one module worker. This storage is measured. The existing immediate classifier consumes/skips payloads and does not retain integer constants or all block payloads for emission; it was not treated as an emission IR. Existing heap-emitter/plugin facilities were inspected as references.

Admission accepts only i32/i64 params and locals and exactly one i32/i64 result, with limits of 256 locals, 512 logical stack entries, 32 nested controls, 64 KiB body and a 16,384-node accounting bound. Admitted opcodes are:

- i32/i64 constants; local.get/set/tee; drop and nop.
- add, sub, mul, and, or, xor, shl, signed/unsigned shr, and integer eq/ne/lt/le/gt/ge comparisons.
- block/if/else/end with inline empty/i32/i64 block types; implicit single-result return and a tail explicit return immediately before the final end.

Loops, arbitrary branches, indexed block types, calls, div/rem, guest memory/global operations, FP/vector/reference operations and custom instructions use function-level fallback. GC/EH module conditions and source/unwind recording also conservatively exclude admission. All potentially trapping or externally observable guest effects are excluded, so the common pending-effect sequence is empty. Trap/load/effect ordering, inline returns, loops, GC roots and exception behavior in those functions stay with the existing compiler. The current target entry checks, calling convention and frame finalization surround the pilot. There is no partial-emission fallback and thus no rollback of emitted code/relocations/metadata to claim.

`WAGO_SHARED_SCALAR=0` selects the established driver for diagnosis. It was unset during candidate measurements. C adds 1,174 production lines while retaining the fallback implementation; it does not yet reduce total compiler source size.

## Measurement method and boundaries

Host: Debian 13, Linux `6.12.111+deb13-amd64`, AMD Ryzen 7 8845HS (8 cores/16 threads), native AMD64, Go `1.27.1`, `GOAMD64=v1`, normal Go optimizer, no PGO or special compiler flags. CPU feature flags, Go environment, tool provenance and OS details are saved in `environment.txt`. The governor was performance, boost enabled and AC online. No deliberate power/thermal change was made; frequency was not locked and ordinary desktop activity was not completely eliminated.

Production timings have no build tags. Bounds checks are the normal explicit mode (no guard-page tag), and runtime/compiler production optimization defaults are unchanged between points. Public defaults are one compilation worker. Primary runs use `GOMAXPROCS=1`, `GOGC=100`, `GOMEMLIMIT=off`, CPU affinity 2. Additional runs use `GOMAXPROCS=4`, affinity 2–5 and compare explicit p1 with the automatic worker policy. The automatic policy is additional characterization, not the public default.

Binaries and fixtures were built before timing. Each of three complete blocks ran **A/B/C/C/B/A**, for six fresh processes per revision; each process used 200 ms per benchmark and count 1. Iterations within a process are not independent samples. No build, test or profile process from this work ran during these final timing blocks. No sample was discarded. `measurement-runs.json` records commands, order, start/elapsed times and exit status. `benchstat` version is recorded. Per-workload tables report medians, its 95% confidence envelope, p values and n=6. Values marked `~` are inconclusive. Many comparisons were made; isolated marginal p values are weaker evidence than large repeatable changes.

- Native compile: already decoded/validated reusable immutable module outside timing; analysis/native compilation and supported output Close inside timing. There is no compiled-output cache in these entry points.
- Full compile: configuration and fixture preparation outside timing; decode, validation, analysis, native codegen and Close inside timing.
- Synthetic execution: compile/instantiate outside timing; Invoke plus exact output check inside timing. Inputs are fixed at 3, local state initializes each call, and cleanup is outside timing. Invocation overhead is included.
- Existing corpus execution: repository prepared-invocation batching, compiled outside timing and exact/semantic oracle before timing. xxHash uses fixed buffers/vectors. JSON-AS uses the established same-instance incremental-GC workload; its internal allocator/GC phase is not reset byte-for-byte each call. Those fallback-heavy JSON execution rows are supplementary steady-state results, not a strict reset-state claim.
- Admission: identical copied admission algorithm/local expansion in all three binaries, decoded inputs outside timing; zero allocation per scan. Actual C function diagnostics also record admission nanoseconds. Only the first function is scanned by the `many`/`large_then_small` microbenchmarks; per-function module admission costs must be summed. Identical probe source still shows some binary-layout/process differences, so its cross-binary percentage is not a semantic algorithm change.

Each entry invokes the compiler, not a reusable artifact: native `CompileModuleWith` creates output each iteration; public `PreparedCompile.Compile` unconditionally calls `compileWithConfigAndInstructions`. Close is checked. No outputs accumulate in compile timing loops. Diagnostics record one function attempt per function, including fallbacks. Stats and profiling run separately from production timing.

Interpretation:

- Fixed-work public allocated bytes fall 2,907,440 (7.70%); allocation counts rise 717 (1.30%). Native allocated bytes fall 2,957,760 (15.37%); allocations rise 630 (10.01%). Aggregate allocation improvement does not erase the roughly doubled many-locals B/op or increased pressure/deep costs.
- Native retained code grows 9,216 bytes (5.51%) and page-rounded payload grows 16,384 (5.88%). Go allocation totals omit these native mappings. Public retained code lives in Go heap because mapping is deferred, and is not additive to HeapAlloc.
- Single-GC release-phase HeapAlloc plateaus near 1.55 MB in A/B/C through three cycles, with no continuing per-cycle growth in this fixed workload. Native release-phase heap is approximately its initial level. Retained public profiles attribute sampled storage to compiled metadata/snapshots and code buffers, not shared scratch.
- **The apparent engine-release heap drop is confounded by an extra GC epoch.** A separate identical `TestSharingGCObservation` leaves Runtime alive: after batch close, A drops 1,551,512→210,376 bytes on the next GC observation; C drops 1,548,872→210,760. Engine close then changes only about 5 KB. This supports delayed output/finalizer reclamation, not a 1.3 MB engine cache. The supported Close path was called; prompt finalizer reclamation was not assumed. These extra-GC diagnostics are labelled separately and do not replace primary results.
- Final public HeapAlloc differs by only +176 bytes (0.08%); the spread overlaps. There is no demonstrated retained shared-scratch leak. HeapInuse, HeapReleased and RSS vary with allocator/scavenger page reuse; they are not compiler payload counters.
- C current RSS is roughly 2 MB higher despite similar post-GC live heap. Approximately 2.2 MB is already present in its initial RSS; retained public RSS minus initial differs by only 196,608 bytes. Binary size grows 68,316 bytes. Startup/code residency and page reuse contribute, but the exact RSS offset is not fully attributed. It must not be relabelled as a shared-scratch allocation. The measured RSS increase remains an unresolved process-memory cost.

## Ranked regressions and investigation

1. **Deep joins:** execution 14.26→38.61 ns (+170.76%); native/full compile +21.94%/+22.30%; code 45→954 bytes (+909, 2,020%), frame 0→40. The common driver canonicalizes both entry and exit of nested result blocks, repeatedly loading/storing homes that the old driver can keep in registers or elide. CPU profiles place roughly a third of candidate deep compile samples in canonicalization. This is the dominant repeatable performance regression.
2. **Pressure execution/storage:** 44.69→48.19 ns (+7.82%), code +56 bytes (6.79%), frame +352 bytes (151.72%), spill high-water 27→70 (+43,159.26%). Reserving canonical operand slots plus separate temporary spill slots and losing some pinned-local choices expands the frame. Allocation rises 19,488→28,856 B/op (+9,368,48.07%) and 18→30 allocations. Profiles identify shared slice construction and free-slot growth; no new per-op instruction object is allocated.
3. **Compiler allocation on many-locals/deep:** many-locals 29,192→58,888 B/op (+29,696,101.73%), 21→31 allocations. Deep 11,504→20,424 (+8,920,77.54%),22→29. Scalar value/local/control slices coexist with the still-reserved legacy arena. Profiles show both shared arena allocation and `newStackWithCap`. Per-module backing growth, not per-small-function adapter allocation, explains these changes.
4. **Process/native retained memory:** peak RSS +2,188 KiB (9.60%), retained page-rounded payload +16,384 bytes (5.88%) for 36 modules. RSS attribution is incomplete as explained above; no retained-heap growth trend was seen.
5. **Leaf/control overhead:** small native compile +2.68% (marginal p=.041), join execution +4.96%, tiny corpus execution +2.45%; many small functions add 2,560 native bytes (17.22%) and summed frames 0→12,288. Ingress homing and conservative return/frame handling sacrifice leaf optimizations. Many execution has a 24% candidate envelope and is not a clean stable regression estimate. The four-capacity p1 many_funcs full compile +2.29% also crosses the aggregate investigation threshold, but automatic-policy change remains inconclusive.

Large-function native compile improves 36.23%, and its allocation decreases because A's historical linked arena grows to 215 KB while the bounded common value arena plus retained original reservation totals about 143 KB. Many-local execution improves 32.71%, with code decreasing 2,832→1,008. These gains are useful, but neither lower source count nor faster compilation establishes memory or execution parity.

The >2% aggregate and >5% important-workload thresholds were used to investigate, not to accept/reject automatically. No workload or sample was dropped after seeing a regression. The design should next preserve clean local homes, elide redundant block agreements and leaf frames, improve spill-slot accounting and make legacy arena reservation lazy for admitted paths. The current pilot is left unchanged to preserve this initial result.
