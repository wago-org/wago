Expected P effects,  not measured conclusions
P leaves the main 16/4 body and four chains unchanged. Its tail alternates accReg/p1,  uses displacement0 for each load,  and advances addr in 32 bits after each load. It preserves scalar wrapping behavior while halving tail backedges. It still updates address and counter once per element and adds an odd-count dispatch. A two-element tail does not get the control savings of H's four-element tail. Its native code and instruction layout are larger/different than D; direct P/D evidence cannot isolate branch frequency or chain parallelism from layout. No speed claim is justified before measurements. Keep n0, short odd/even counts, n16/17, all relevant remainders, unaligned8192, andstreaming outcomes visible. Inspect emitted hot/tail instructions and register/stack statistics before claiming the intended design executed. Specific pair-tail markers now exist in kernel and corpus assertions.

Expected DR effects and limits
At compile.go:1917-1931,  DR adds headroom while already summing body bytes. The helper uses existing loop/memory/signature hints and allocates no new object itself. Activation is restricted to reserve enabled, 16/4, noH/noT, deferred mapping, one worker, noncompact. Normal stubs return false/zero; verify old/new normal controls rather than infer no runtime cost from source alone.
The128 B/function, 1024 B/module cap is a logical code capacity cap,  not a total allocated-byte cap. compileModuleParallel initializes both worker arena and joined code from this capacity,  so one worker can reserve it twice. Heap size-class rounding can add further cost. memory.wasm logical capacity 496->624 should use Go classes 512->640 twice: approximately256 extra B versus normal baseline, while avoiding two 896 B growth objects versus D. A passed108-allocation test proves allocation-count restoration for this module, not equal allocated bytes or faster public compilation. Record all bytes/count/time/lifecycle rows. Label unchanged memory use only if bytes also support it.

False positives need evidence
sumUnrollCodeHeadroom in sum_unroll_experimental.go qualifies a body <=2048 B with loop and memory hints, no calls/tailcalls/SIMD/bulkmemory, and a first result i64. This is much broader than specialized sum admission. Stores, pointer loops, unsupported sum shapes, shared memory/memory64, unpinned locals, failed range proofs, and multiple-result functions whose first result is i64 can qualify without emission. The hint is correctly only allocation advice; it does not need to prove a sum. However,  DR can increase memory/time in such modules. The cap limits damage but does not establish profitability.
Before timing,  record requested headroom and eligible-function indices/counts per corpus module in a diagnostic audit,  with native sum admission counts. This identifies which zero-emitter controls actually exercise the hint. If none of the chosen control modules receives headroom,  add a fixed small i64-return memory loop rejected by the recognizer as a false-positive compile/lifecycle control,  or explicitly leave the false-positive cost unvalidated. Do not call a corpus test with no headroom a test of hint false-positive cost. A larger module with several qualifying non-sum functions can test the 1024 B logical cap and duplication cost without expanding the optimization.
Memory native byte hashes must match D for DR and P for PR,  including negative controls; reserve is not intended to alter instruction bytes. Verify private setter selection and reset: DR chooses D emission plus reserve, PR chooses P emission plus reserve. Baseline must disable both. Timers must not invoke setters. Existing single-process AllocsPerRun 25 count check is useful correctness evidence but is not the 20-sample benchmark.
