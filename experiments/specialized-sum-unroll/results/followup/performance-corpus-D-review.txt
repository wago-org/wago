3. Body sizes from diagnostic records are 36+44=80 bytes. moduleCodeCapacityAMD64 at compile.go:742-747 uses TaperedModuleCodeCapacity(80,2,40,37,...), which returns 496 logical bytes (capacity.go:92-111).
4. Baseline worker output is 158+312=470 bytes; final output includes 2 padding bytes, total472. Both fit496. D worker output is 158+375=533; final total535. Both exceed496.
5. ws.arena append at compile.go:2284 and final join append at compile.go:2387 each grow from capacity496. JoinedModuleCodeCapacity at capacity.go:75-85 never raises the initial496 estimate.
6. Local Go1.27.1 nextslicecap uses 496+(496+3*256)>>2 = 812 bytes before allocator rounding. Byte allocation size-class rounds this to896. The two additional grow allocations account for 896+896=1792 bytes and +2 allocations exactly.
7. Raw serial code uses a mapped CodeBuffer, rounded to an OS page, so both outputs fit without an added Go heap allocation. This explains the observed split between raw backend and public costs.
