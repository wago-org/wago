The instantiation cases each report 1,464 B/op and six Go heap allocations. Inspect native memory setup, data initialization, and cleanup before assuming Go allocation is the main cause. The benchmark includes `Close`. The cause needs a CPU profile and, for page operations, system-level measurements.

The command benchmark creates WASI imports, instantiates the module, invokes its command, and closes the instance on each iteration. The wazero benchmark prepares its WASI host module outside the timed loop. This setup difference is an important place to inspect. Wago uses fewer bytes for cjson and tinyxml2 (38,472 and 39,112 B/op), but makes more individual allocations. These results do not isolate guest execution time.

Automatic workers increase time per operation by 14.2% for concurrent many_funcs compilation and 9.6% for concurrent json-as compilation. The current default is one worker (`src/wago/config.go:352`); this finding concerns explicit automatic mode. For single-module json-as compilation, eight workers improve time by only 1.8% over four workers while increasing bytes allocated by 33.2%. Inspect worker limits and per-worker scratch storage.

## Other observations

Wago full compilation was faster in all 80 paired workloads. Wago execution was faster in 69 of 72 paired cases, and all 72 Wago execution cases reported zero B/op and zero allocs/op. The exceptions were fastfloat (+3.1%), raytrace (+3.0%), and monocypher (+0.3%). These small gaps need repeated measurements before code changes.

The benchmark runner itself has a cost: `BenchmarkMemoryGrowSuccess` creates and closes an instance outside the timer for every measured growth call. Millions of iterations made these cases take several minutes. Inspect `bench/suite/bench_test.go:266` if reducing suite duration is a goal.

`benchmarkExecCalls` normalizes ns/op to one call, but leaves Go's allocation metrics per batch (`bench/suite/suite_test.go:595`). Divide B/op and allocs/op by calls/batch for per-call comparisons. Go heap metrics also exclude memory acquired through native mappings.

This is one measurement per case, with engines run in separate groups. It identifies candidates; it does not establish a regression or a confirmed cause. The older saved capture uses a different commit and benchmark setup, so it was not used as a regression baseline. No source code was changed.
