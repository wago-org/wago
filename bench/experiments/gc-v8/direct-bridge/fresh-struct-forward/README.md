# Fresh scalar struct forwarding in the direct pipeline

This reuses the existing bounded scalar-local forwarding proof. It does not
elide construction, payload initialization, root-array storage, allocation
accounting or collection. No runtime performance improvement is claimed yet.

## Why the real artifact missed the existing optimization

The exact retained struct workload constructs a one-field scalar object from its
induction local, assigns it to a reference local, stores it in the roots array,
and then reads its field. The existing fresh-struct fact already supports that
shape. However, direct build tags also set `gcHelperOnly` to exclude
handle-specific lowering. That disabled both fact capture and consumption. In
addition, native read lowering appeared before the forwarding check, consuming
the receiver first. Fixing ordering alone was insufficient; both observed failed
receipt attempts are retained.

The fix allows this representation-independent scalar-local fact in direct-read
pipelines and tries it before native reads. Pure helper-only mode remains
unchanged. No other handle-specific path is enabled; compact fact admission is
not expanded. The fact is still limited to one unpacked scalar field, exact
type/field identity and an unchanged borrowed reference local. Source/object
assignments, mutations, calls and control boundaries retain their invalidation
rules. Constructor and root-store traps remain observable.

## Controlled comparison

The opt-in `wago_gc_fresh_struct_probe` tag exposes an experimental, default-OFF
per-compilation option `gc-fresh-struct-forward`. The normal fixed build has no
new catalog entry and uses the fixed existing policy. In a probe build, explicit
`WithOptimization("gc-fresh-struct-forward", false/true)` selects the mode
without mutating process globals.

Use ONE exact-seven-pipeline-tags-plus-probe binary for both modes:
- Runtime bridge: `GC_BRIDGE_FRESH_STRUCT_FORWARD=0` or `1`.
- Compile+Close probe: `GC_COMPILE_FRESH_STRUCT_FORWARD=0` or `1`.

The runtime JSON records the explicit override. Unset is OFF in the probe
build, not evidence of an enabled candidate. Off/on/off diagnostic compilation
requires exact struct forwarding receipts0/1/0, and compares generated bytes,
not just sizes, for every non-forwarded control.

Hypothesis: re-reading the unchanged scalar local avoids the arena-pointer,
null-check and field-load sequence in the struct loop. Allocation and collector
work remain; the effect may be modest or outweighed by register/code-layout
changes. Separate-binary results are not sufficient evidence. No gain is
expected for cases without a valid fresh fact.

## Qualification results

Final production/probe source `1e9dba8b`, Go1.27.1 linux/amd64. Independent source
review found no blocker in either the bounded forwarding carveout or immutable
per-compilation comparison hook.

- Default catalog/backend/full Wago runtime: PASS0.016s/19.935s/75.769s.
- Exact seven-tag pipeline plus probe, codegenstats and register checker:
  PASS0.099s. Active fixtures assert their forwarding/rejection receipts.
- Concurrent explicit off/on configurations and separate instances, including
  exact allocation counts and forced movement: race detector PASS1.108s.
- i64/f32/f64 payload bits (including NaN payloads and signed zero) survive forced
  movement. Source overwrite, field mutation and reference-local null overwrite
  reject forwarding; root-array bounds failures still trap. Every fixture
  retains its expected allocation count.
- Exact struct artifact off/on/off: forwarding0/1/0; generated1775/1711/1775 bytes.
  All five non-forwarded controls have identical generated bytes across modes.

The single comparison binary has SHA256
`a76400feceef5dbcfac8c175e8bc16f50648800b398b0aef4ca39270f3d2470f`.
See `qualify.sh` for exact build tags and checks. No runtime timing or compile
benchmark was executed during this qualification stage; smaller code is not a
measured speedup. TinyGo and a full experimental-tag runtime suite are not
claimed by this stage.

Failed attempts are preserved: the baseline receipt failed with zero forwarding;
the ordering-only fix also failed because helper-only admission still blocked
fact creation. A temporary trace confirmed a valid pinned-local candidate; no
trace code remains. The first full-default run rejected newly added direct-only
fixtures because they lacked experimental build scoping. Their build constraint
was corrected and the full default gate rerun successfully. This was a test
admission mistake, not a relaxed runtime-admission rule.

## Current disposition

The candidate remains unpromoted. Matched runtime evidence is retained separately: fresh-forward-samebinary or gc-single-clear-matched, respectively. `candidate.patch` preserves the qualified source delta and tests for isolated reproduction; it is not applied to production here. Private execution prefixes in archived logs are omitted.
